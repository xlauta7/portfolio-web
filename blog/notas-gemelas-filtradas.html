Notas gemelas filtradas: por qué reutilizar XOR rompe el secreto

Dos mensajes cifrados con la misma secuencia XOR, un prefijo conocido y la diferencia entre demostrar un resultado e inferirlo.

16 octubre 2026 · 50 puntos nominales · Fácil · Lautaro Poggi (xLauta7)

Sobre la autoría y la evidencia: El cuaderno registra la recuperación de flag{crypto_two_time_pad}, pero no conserva confirmación independiente del envío en el tablero. El supuesto sobre espacios en el primer mensaje fue una hipótesis, no un dato garantizado.

01. Dos textos cifrados, una pista

El reto incluía un ZIP con dos valores hexadecimales de 64 bytes cada uno y un README. Sabíamos que el mensaje A comenzaba por MEMO-01: y que ambos mensajes habían usado la misma secuencia de clave XOR. Mi primera pregunta fue cómo aprovechar una pequeña parte conocida del mensaje sin conocer la clave.

02. El error criptográfico

Si dos mensajes se cifran con la misma clave o flujo de bytes XOR, combinar los cifrados elimina la clave repetida. Ésta es la idea de un two-time pad.

text
C_A = P_A XOR K
C_B = P_B XOR K

C_A XOR C_B = P_A XOR P_B
P_B = C_A XOR C_B XOR P_A

El primer resultado útil salió de aplicar la información realmente disponible: los ocho bytes iniciales MEMO-01:. Con ellos se recuperó flag{cry al comienzo del segundo mensaje. Hasta ahí existía una deducción apoyada por el prefijo conocido.

03. La hipótesis que completó el texto

Para avanzar más allá de ocho bytes, propuse que el mensaje A ocupaba los 64 bytes y estaba rellenado con espacios después de MEMO-01:. Bajo esa suposición apareció la cadena flag{crypto_two_time_pad}. Ese salto no debe confundirse con una deducción matemática obligatoria: dependía de cómo suponíamos que era el resto del mensaje A.

04. Reconstrucción reproducible en PowerShell

Los nombres reales de los dos archivos del ZIP no constan en el registro, así que se usan A.txt y B.txt como marcadores. Cada archivo debe contener 128 caracteres hexadecimales, equivalentes a 64 bytes.

powershell
$hexA = (Get-Content "A.txt" -Raw) -replace '\s',''
$hexB = (Get-Content "B.txt" -Raw) -replace '\s',''
[byte[]]$a = 0..(($hexA.Length / 2) - 1) | ForEach-Object {
    [Convert]::ToByte($hexA.Substring($_ * 2, 2), 16)
}
[byte[]]$b = 0..(($hexB.Length / 2) - 1) | ForEach-Object {
    [Convert]::ToByte($hexB.Substring($_ * 2, 2), 16)
}
[byte[]]$supuestoA = [System.Text.Encoding]::ASCII.GetBytes(
    "MEMO-01:" + (" " * 56)
)
[byte[]]$supuestoB = for ($i = 0; $i -lt 64; $i++) {
    [byte]($a[$i] -bxor $b[$i] -bxor $supuestoA[$i])
}
[System.Text.Encoding]::ASCII.GetString($supuestoB)

El operador -bxor realiza XOR bit a bit; Substring toma pares de dígitos hexadecimales y ToByte(...,16) los convierte a valores de byte.

05. Aprendizajes y siguiente práctica

  • Reutilizar el mismo flujo XOR entre mensajes compromete su confidencialidad.
  • Conocer un prefijo revela solo la parte correspondiente del otro mensaje; no todo el texto.
  • Una hipótesis puede ayudar a progresar, pero debe identificarse como hipótesis.
  • Quiero repetirlo sin IA: probar primero ocho bytes y justificar cualquier inferencia posterior.

Esta experiencia fue valiosa precisamente porque me obligó a distinguir entre el resultado que busco y la evidencia que realmente lo sostiene.
