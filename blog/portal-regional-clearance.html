Portal regional Clearance: un login vulnerable a NoSQL Injection

Cómo una API que aceptaba objetos JSON en el campo de contraseña permitió modificar la lógica de autenticación de un reto CTF.

16 octubre 2026 · 35 puntos nominales · Fácil · Lautaro Poggi (xLauta7)

Sobre la autoría y la evidencia: Este artículo documenta un reto CTF autorizado, no un hallazgo en producción. La prueba funcionó según mis apuntes, pero el comando de curl fue reconstruido después; el endpoint se debe verificar contra la documentación original si se reproduce.

01. La aplicación y su superficie

El desafío era un portal regional con documentación pública de la API en /api/docs/. La documentación mostraba la solicitud POST /api/login. Había un detalle llamativo: el campo password podía recibir objetos JSON, no solo una contraseña de texto.

Antes de buscar un bypass se estableció un caso de control: con guest/guest, la respuesta indicaba el rol guest. Una contraseña literal incorrecta fallaba. Estos controles importaban para interpretar qué cambiaba con cada prueba.

02. Hipótesis: operadores en lugar de contraseñas

En algunas bases de datos NoSQL, el operador $ne expresa «no igual a». Si una aplicación incorpora directamente un objeto recibido del cliente en su consulta, un campo que debería ser una contraseña puede convertirse en una condición lógica. El problema no es usar NoSQL: es permitir que datos de entrada alteren la estructura de la consulta.

json
{
  "username": "admin",
  "password": {"$ne": null}
}

El punto decisivo está en el tipo del valor: password contiene un objeto con un operador, no una cadena de texto. Si el backend no obliga a que sea una cadena y concatena la entrada en la consulta, puede producirse una autenticación no deseada.

03. Solicitud reconstruida

Durante el reto se envió una contraseña en forma de objeto JSON. La variante con admin permitió recuperar el resultado registrado. Ésta es una reconstrucción de la solicitud para uso exclusivo dentro del laboratorio del CTF:

bash
curl -s -X POST \
  'https://challenges.hackrocks.com/regional-clearance-portal/api/login' \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":{"$ne":null}}'

La opción -X POST establece el método; -H declara JSON; -d envía el cuerpo. Es importante comparar la respuesta con la autenticación fallida del control negativo, no interpretar cualquier 200 OK como una explotación.

04. Resultado y alcance

En el cuaderno maestro quedó registrada la flag flag{web_nosql_clearance3}. Es un resultado del desafío, no evidencia de un sistema real expuesto.

Esta prueba enseñó que el análisis de una aplicación empieza por leer sus contratos: documentación, parámetros esperados, tipos de datos y respuestas. También fue un buen ejemplo de por qué registrar el caso de control evita conclusiones apresuradas.

05. Mitigación y lecciones

  • Validar que username y password tengan el tipo esperado antes de usarlos.
  • No interpolar objetos arbitrarios del cliente como operadores de consulta.
  • Utilizar mecanismos seguros de consulta y autenticación, con manejo adecuado de errores.
  • Probar controles negativos y positivos, y conservar evidencia de las diferencias.

Mi próxima repetición autónoma consiste en leer la documentación primero, justificar cada campo y reconstruir la hipótesis sin copiar el payload. El objetivo es aprender el patrón, no memorizar una bandera.
